# 00 · 设计文档索引与关键决策

## 1. 文档定位

本套文档是「基于 RAG 的金融制度类知识问答系统」的**初步方案设计**成果，目标是：

1. 把课题描述中的验收指标（1000 条知识点 / 2 秒响应 / 85% 准确率）还原为**可测量、可验证**的工程设计约束；
2. 冻结一期开发所需的**接口契约、数据模型、模块边界**，使后端、前端、测试可以并行开工；
3. 记录**技术选型理由**，避免开发中期反复推翻方案。

技术选型原则：**一期只使用最经典、社区最成熟、资料最丰富的方案**，不引入冷门依赖与过度设计。
所有进阶能力（增量更新、时效标注、可信度评分、收藏与历史）在数据模型与接口上**预留位置**，
但实现深度按 `docs/10` 的优先级分批交付。

## 3. 术语表（全文统一口径，开发时不得混用）

| 术语 | 英文 / 字段 | 定义 |
| --- | --- | --- |
| **知识库** | `knowledge_base` / `kb` | 按业务条线划分的文档集合，一期固定三个：银行监管、证券行业、保险制度 |
| **文档** | `document` | 一份上传的原始制度材料（一个 PDF / Word / 图片算一份） |
| **切片** | `chunk` | 文档解析后用于向量化的最小检索单元，`chunk_size=500` 字，重叠 `80` 字 |
| **知识点** | `knowledge_point` | **人工可读、可校验的最小制度事实**（如「某办法第 25 条规定的流动性覆盖率下限」）。验收指标「1000 条以上核心知识点」统计的就是这张表 |
| **条文** | `article` | 制度文本中「第 X 条」级别的自然段。它是切片的**切分依据**，不单独建表，作为 `chunk.article_no` 记录 |
| **引用 / 溯源** | `citation` | 答案中 `[1][2]` 角标与切片、文档、页码的映射关系 |
| **可信度** | `confidence` | 0~1 的融合评分，用于前端展示星级与低分告警 |
| **时效状态** | `timeliness` | `effective` 现行有效 / `amended` 已修订 / `repealed` 已废止 / `unknown` 未知 |
| **拒绝回答** | `refused` | 检索证据不足时系统的兜底行为，**不算答错**，但计入单独指标 |

## 4. 架构决策记录（ADR）

> 每条 ADR 记录「结论 + 理由 + 代价」。**后续若需变更，请在本文档追加 ADR-xx，不要静默改代码。**

### ADR-01：一期选用 Milvus standalone 单机模式

- **结论**：使用 `milvusdb/milvus:v2.4.x` standalone + etcd + MinIO，由 docker-compose 编排。
- **理由**：课题明确推荐 Milvus；standalone 模式足够支撑 10 万级向量（本项目约 1~3 万切片），
  且与分布式模式 API 完全一致，未来扩容无需改代码。
- **代价**：单机无高可用；首次拉镜像约 1.5GB。

### ADR-02：向量维度固定 1024，使用 bge-large-zh-v1.5 / BGE-M3

- **结论**：`embedding` 字段 `FLOAT_VECTOR, dim=1024`，模型通过本地 `sentence-transformers` 加载。
- **理由**：中文制度文本上 bge 系列显著优于通用英文模型；1024 维在精度与存储间平衡良好；
  本地推理无 API 费用、无网络依赖，答辩现场可控。
- **代价**：镜像体积增大（约 1.3GB 模型权重），首次部署需下载模型或挂载离线权重目录。
- **备选**：若无 GPU 且 CPU 推理过慢，可切换阿里云 `text-embedding-v3`（1024 维，接口兼容），
  仅需改 `.env` 的 `EMBEDDING_PROVIDER`。

### ADR-03：LLM 走 OpenAI 兼容协议，不绑定单一厂商

- **结论**：使用 `langchain-openai` 的 `ChatOpenAI`，通过 `base_url + api_key + model` 三参数切换厂商。
- **理由**：DeepSeek、通义千问、智谱、Kimi、vLLM 本地部署均提供 OpenAI 兼容端点，
  课程/答辩环境下可随时降级到备选渠道。
- **代价**：无法使用各厂商私有高级特性（可接受）。

### ADR-04：一期关键词检索用 MySQL FULLTEXT(ngram)，不引入 Elasticsearch

- **结论**：`document_chunk.text` 建 `FULLTEXT ... WITH PARSER ngram`，关键词通道走 MySQL。
- **理由**：少维护一个中间件，降低部署与答辩环境的不确定性；一期数据量（1~3 万切片）下性能足够。
- **代价**：中文分词质量弱于 ES/IK；二期若检索召回不达标，按 ADR-04-b 引入 ES 或 Milvus BM25 稀疏向量。

### ADR-05：一期不引入重排模型，但预留 Reranker 接口

- **结论**：`Retriever` 输出的 `rerank` 环节默认实现为「按融合分数截断 Top-5」，
  通过 `RERANK_ENABLED=false` 关闭；接口签名与 bge-reranker 完全一致。
- **理由**：重排能明显提升精度但增加 100~300ms 延迟，先保证 2 秒时延达标，再按需开启。

### ADR-06：一期不引入 Redis 与消息队列，入库任务用数据库表轮询

- **结论**：`ingest_task` 表记录入库进度，FastAPI `BackgroundTasks` 执行解析；
  前端按 1.5s 轮询 `GET /api/v1/tasks/{id}`。
- **理由**：避免为 MVP 引入 Celery/RabbitMQ 的运维复杂度。
- **代价**：不支持多副本水平扩展（单后端实例），重启后未完成任务标记为 `failed` 可重试。
- **触发升级条件**：并发入库需求 > 5 份文档，或单文档解析超过 5 分钟。

### ADR-07：答案响应统一使用 SSE 流式，同时提供非流式接口

- **结论**：`POST /qa/ask/stream`（SSE，前端默认使用）与 `POST /qa/ask`（一次性 JSON）。
- **理由**：LLM 完整生成通常 2~6 秒，非流式无法满足「2 秒内看到响应」的体感；
  SSE 让首 token 在 1~1.5 秒内到达，满足指标定义（见 `docs/09` 第 5 节的时延口径）。

### ADR-08：认证采用 JWT + RBAC 三角色，一期不做细粒度权限

- **结论**：角色 `admin`（知识库管理）/ `editor`（文档上传、知识点校验）/ `viewer`（问答检索）。
- **理由**：覆盖校企合作演示与验收所需的权限区分，不做部门/数据行级权限。

### ADR-09：知识点与切片是多对多且弱耦合

- **结论**：`knowledge_point` 独立建表并单独向量化入 Milvus（`source_type=knowledge_point`），
  同时通过 `knowledge_point_source` 关联其来源切片。
- **理由**：1000 条知识点是本项目的**核心资产与验收指标**，必须独立可维护、可人工编辑、
  可脱离原始文档存在；而切片是机器产物，重新解析会全量重建。两者生命周期不同，必须解耦。
- **代价**：检索时需要同时召回两类实体并去重（在 `docs/05` 第 4 节定义去重规则）。

## 5. 一期范围与非目标

| 属于一期（Must） | 明确不做（Out of Scope） |
| --- | --- |
| 三类知识库、文档上传解析、OCR | 多租户隔离、组织架构 |
| 关键词检索 + 向量检索 + 混合检索 | 全文搜索引擎集群、图谱数据库 |
| 自然语言问答 + 答案溯源（页码/条文级） | 语音问答、多模态图片问答 |
| 条文关联查询（知识点关联条文） | 制度自动比对/差异分析 |
| 收藏、问答历史、知识点人工校验 | 移动端 App、小程序 |
| Docker 部署、pytest + Apifox 测试 | K8s 编排、CI/CD 流水线（列为加分项） |

## 6. 变更管理约定

1. 接口变更 → 先改 `docs/06`，再改代码；前端与 `apifox/FinRAG-collection.json` 同步更新。
2. 表结构变更 → 先改 `docs/03` 与 `deploy/mysql/init/01-schema.sql`，再生成 Alembic 迁移。
3. Prompt 变更 → 必须更新 `docs/05` 第 6 节的 Prompt 版本号，并在评测集上回归，准确率不得下降。
4. 所有文档中的**常量**（端口、维度、chunk 参数、错误码）以本文档与 `docs/03`、`docs/06` 为准，
   代码中不得硬编码，统一读 `.env` 或常量模块。
