# 06 · 后端接口设计

> 本文档是**前后端并行的唯一契约**。接口路径、字段名、错误码在此冻结；
> 任何变更必须先改本文档，再改代码，并同步 `apifox/FinRAG-collection.json`
> （接口调试与自动化测试使用 **Apifox**，导入方式见 `apifox/README.md`）。

## 1. 通用约定

| 项 | 约定 |
| --- | --- |
| Base URL | `/api/v1`（开发直连 `http://localhost:8000`，生产经 Nginx `http://host:8080`） |
| 协议 | HTTP/1.1，JSON（`Content-Type: application/json; charset=utf-8`） |
| 文件上传 | `multipart/form-data` |
| 流式问答 | `text/event-stream`（SSE） |
| 鉴权 | 请求头 `Authorization: Bearer <access_token>` |
| 链路追踪 | 请求头 `X-Request-ID`（可选，服务端生成后原样回传） |
| 时间格式 | `YYYY-MM-DD HH:mm:ss`（本地时区 UTC+8）；日期字段 `YYYY-MM-DD`；ISO8601 用于时间戳 |
| ID 类型 | 整数 ID 用 `number`（JS 安全整数范围内）；`session_no`/`task_no` 用字符串 |
| 分页 | 请求 `page`（默认 1，≥1）、`size`（默认 10，1~100）；响应统一 `total/page/size/pages` |
| 排序 | 未指定时按 `created_at DESC` |
| 字符编码 | 全链路 UTF-8 |
| 接口文档 | `http://localhost:8000/docs`（Swagger UI，自动生成，作为联调对照） |

## 2. 统一响应结构

**成功**

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "request_id": "3f9a1c2e7b4d4a8e"
}
```

**失败**

```json
{
  "code": 40103,
  "message": "用户名或密码错误",
  "data": null,
  "request_id": "3f9a1c2e7b4d4a8e"
}
```

**规则**

1. HTTP 状态码表达**传输语义**（200/400/401/403/404/409/413/422/429/500），
   `code` 表达**业务语义**，两者同时正确设置。
2. `message` 必须是**面向最终用户的中文**，可直接展示；技术细节只写日志。
3. 分页响应 `data` 结构统一为：

```json
{
  "total": 1234, "page": 1, "size": 10, "pages": 124,
  "items": [ ]
}
```

4. 字段命名统一 `snake_case`（与数据库一致，减少心智负担）。
5. 可空字段统一返回 `null`，不省略键（便于前端类型稳定）。

## 5. 详细接口定义

### 5.1 认证 `/auth`

#### POST `/auth/register`

```json
// 请求
{ "username": "zhangsan", "password": "Passw0rd!", "real_name": "张三",
  "email": "z@example.com", "invite_code": null }
// 响应 data
{ "id": 2, "username": "zhangsan", "role": "viewer", "created_at": "2025-06-01 10:00:00" }
```

规则：`username` 4~50 位字母数字下划线；`password` 8~32 位且需含字母与数字；
默认角色 `viewer`；`invite_code` 与 `.env` 的 `EDITOR_INVITE_CODE` 匹配时授予 `editor`。

#### POST `/auth/login`

```json
// 请求
{ "username": "admin", "password": "Admin@123" }
// 响应 data
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 28800,
  "user": { "id": 1, "username": "admin", "real_name": "系统管理员", "role": "admin" }
}
```

失败：`40103`（用户名或密码错误）、`40301`（账号禁用）。

#### GET `/auth/me`

```json
// 响应 data
{ "id": 1, "username": "admin", "real_name": "系统管理员", "role": "admin",
  "email": null, "last_login_at": "2025-06-01 09:59:00" }
```

#### POST `/auth/logout`

无状态实现，返回 `{"code":0,"message":"success","data":null}`；前端负责清除本地 token。

### 5.2 系统 `/health` `/system/config` `/stats`

#### GET `/health`

```json
{
  "code": 0, "message": "success",
  "data": {
    "status": "ok",
    "version": "1.0.0",
    "uptime_seconds": 3600,
    "dependencies": {
      "mysql":  { "status": "ok", "latency_ms": 3 },
      "milvus": { "status": "ok", "latency_ms": 8, "collection": "finrag_embedding", "entities": 31842 },
      "llm":    { "status": "ok", "model": "deepseek-chat", "latency_ms": 412 },
      "ocr":    { "status": "ok", "langs": ["chi_sim", "eng"] },
      "embedding": { "status": "ok", "model": "bge-large-zh-v1.5", "dim": 1024 }

  }
}
```

任一依赖异常时 `status` 为 `degraded`，`dependencies.x.status` 为 `error` 并附 `message`。
**该接口不鉴权**，供 Docker healthcheck 与运维使用，HTTP 状态始终 200。

### 5.4 文档 `/documents`

#### POST `/documents/upload`

`multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `files` | File[] | 是 | 支持多文件，单文件 ≤ 50MB |
| `kb_id` | int | 是 | 所属知识库 |
| `title` | string | 否 | 不传则自动从文件名/正文推断 |
| `doc_no` | string | 否 | 文号 |
| `doc_type` | string | 否 | 默认 `regulation` |
| `issuing_authority` | string | 否 | 发布机构 |
| `publish_date` | date | 否 | |
| `effective_date` | date | 否 | |
| `expiry_date` | date | 否 | |
| `timeliness` | string | 否 | 默认 `unknown` |
| `keywords` | string | 否 | 逗号分隔 |

> 多文件上传时元数据字段**应用到全部文件**；若需逐个设置，前端先单个上传或上传后调用
> `PUT /documents/{id}` 修正。

```json
// 响应 data（degraded=false 表示全部成功受理）
{ "results": [
    { "file_name": "流动性风险管理办法.pdf", "success": true,
      "document_id": 18, "task_no": "t_20250601120000_ab12cd", "status": "pending" },
    { "file_name": "重复文件.pdf", "success": false, "code": 40901,
      "message": "该文件已存在于本知识库", "document_id": 12 }
  ],
  "accepted": 1, "rejected": 1
}
```

#### GET `/documents`

查询参数：`kb_id`、`category`、`status`、`doc_type`、`timeliness`、`keyword`（标题/文号模糊）、
`page`、`size`、`sort`（`created_at` / `publish_date`）。

```json
{ "data": { "total": 213, "page": 1, "size": 10, "pages": 22, "items": [
  { "id": 18, "kb_id": 1, "title": "商业银行流动性风险管理办法", "doc_no": "银保监会令2018年第3号",
    "doc_type": "regulation", "category": "banking", "issuing_authority": "原中国银保监会",
    "publish_date": "2018-05-23", "effective_date": "2018-07-01", "expiry_date": null,
    "timeliness": "effective", "is_latest": 1, "version": 1,
    "file_name": "流动性风险管理办法.pdf", "file_size": 2097152, "page_count": 32,
    "parse_method": "text", "status": "ready", "chunk_count": 186,
    "error_message": null, "created_at": "2025-06-01 12:00:00" } ] } }
```

#### GET `/documents/{doc_id}`

在列表字段基础上追加 `file_ext`、`file_md5`、`keywords`、`uploaded_by`、
`superseded_by`、`warnings`。

#### DELETE `/documents/{doc_id}`

级联动作（见 `docs/03` §6）：
1. 删除 `document_chunk`；
2. 删除 Milvus 中 `document_id == {doc_id}` 的实体；
3. 清理 `knowledge_point_source` 中指向该文档切片的关联；
4. 受影响知识点 `primary_chunk_id` 置空，`verify_status` 置 `doubted`；
5. `document.status = 'archived'`（物理文件保留，提供 `?hard=true` 彻底删除）。

```json
{ "data": { "document_id": 18, "deleted_chunks": 186, "deleted_vectors": 186,
            "affected_knowledge_points": 7 } }
```

#### GET `/documents/{doc_id}/chunks`

```json
{ "data": { "total": 186, "page": 1, "size": 20, "pages": 10, "items": [
  { "id": 8891, "chunk_index": 25, "chapter_no": "第三章", "article_no": "第二十五条",
    "page_start": 12, "page_end": 12, "char_count": 412,
    "source_type": "text", "embedding_status": 1,
    "raw_content": "商业银行的流动性覆盖率应当不低于100%。……" } ] } }
```

> 列表接口**不返回** `content`（带前缀的大字段），避免响应体过大。

#### POST `/documents/extract-meta`（P1）

上传单文件 → 只做解析与元数据抽取，**不落库**，返回预填表单：

```json

            "char_count": 42180, "detected": {
              "title": "商业银行流动性风险管理办法", "doc_no": "银保监会令2018年第3号",
              "issuing_authority": "原中国银行保险监督管理委员会",
              "publish_date": "2018-05-23", "effective_date": "2018-07-01" },
            "preview_text": "第一章 总则\n第一条 为加强商业银行流动性风险管理……" } }
```

### 5.5 入库任务 `/tasks`

#### GET `/tasks/{task_no}`

```json
{ "data": {
  "task_no": "t_20250601120000_ab12cd", "document_id": 18, "kb_id": 1,
  "task_type": "ingest", "status": "embedding", "progress": 65,
  "stage_message": "正在向量化切片 121/186", "total_chunks": 186, "done_chunks": 121,
  "error_message": null, "duration_ms": 45210,
  "started_at": "2025-06-01 12:00:02", "finished_at": null } }
```

`status` 取值与前端展示映射：

| status | progress | 前端文案 | 颜色 |
| --- | --- | --- | --- |
| `queued` | 0 | 排队中 | 灰 |
| `parsing` | 10 | 正在解析文档 / OCR 识别中 | 蓝 |
| `cleaning` | 35 | 正在清洗文本 | 蓝 |
| `chunking` | 45 | 正在切分条文 | 蓝 |
| `embedding` | 50~85 | 正在向量化切片 x/y | 蓝 |
| `indexing` | 90 | 正在写入向量库 | 蓝 |
| `success` | 100 | 已完成 | 绿 |
| `failed` | — | 失败（展示 `error_message`） | 红 |

前端轮询间隔 **1.5 秒**，`success`/`failed` 后停止轮询并刷新文档列表。

#### POST `/qa/ask/stream`（SSE）

**响应头**

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no          ← 关键：关闭 Nginx 缓冲，否则 SSE 被攒批
```

**事件序列**

```
event: meta
data: {"message_id":10231,"session_no":"s_...","citations":[...],"answer_type_pending":true}

event: token
data: {"delta":"根据《商业银行流动性风险管理办法》"}

event: token
data: {"delta":"第二十五条，商业银行的流动性覆盖率应当不低于100%[1]。"}

event: ping
data: {"ts":1748764800}          ← 每 15 秒一次，防代理层断连

event: done
data: {"answer_type":"answered","confidence":0.874,"confidence_level":"high",
       "latency_ms":1480,"latency_detail":{...},"token_usage":{...},
       "used_citations":[1],"suggestions":["..."]}

event: error
data: {"code":50030,"message":"大模型服务暂时不可用，已为您展示检索到的相关条文"}
```

**规则**

1. `meta` 事件**必须在检索完成后立即下发**，不等 LLM 首个 token（这是 2 秒体感指标的实现基础）。
2. `token` 事件的 `delta` 是**增量文本**，前端直接追加；服务端不发送累积全文。
3. 正常结束发 `done` 后关闭；异常发 `error` 后关闭。
4. 客户端断开（用户关页面）时服务端必须取消 LLM 请求并**仍把已生成内容落库**，
   避免 token 浪费与历史缺失。
5. 浏览器原生 `EventSource` 不支持 POST，前端必须使用 `fetch` + `ReadableStream`
   手动解析 SSE（实现见 `docs/07` §7）。

## 6. 鉴权、限流与安全约定

| 项 | 规则 |
| --- | --- |
| 凭证 | JWT，HS256，`exp` = 8 小时；载荷仅含 `sub`(user_id)、`username`、`role`、`exp`、`iat` |
| 密码 | bcrypt cost=12；接口响应与日志中**永不出现** `password_hash` |
| 限流 | 问答接口 20 次/分钟/用户；上传接口 10 次/分钟/用户；其他 120 次/分钟/用户。超限返回 `42900` + `Retry-After` |
| 上传安全 | 扩展名白名单 + `Content-Type` 嗅探 + 文件头魔数校验 + 大小限制；文件名服务端重命名（`{uuid}.{ext}`），不使用用户原始文件名做路径 |
| XSS | `/search` 的高亮结果、答案中的制度原文在返回前做 HTML 转义 |
| SQL 注入 | 全部走 SQLAlchemy 参数化；禁止 f-string 拼接 SQL |
| 路径穿越 | 文件读写一律用**数据库中的绝对路径**，不接受前端传入路径参数 |
| 错误信息 | 响应中的 `message` 为可读中文；堆栈、SQL、内部类名只进日志 |

## 7. 与 Apifox / pytest 的对应关系

### 7.1 Apifox（接口调试与自动化测试）

- 导入文件：`apifox/FinRAG-collection.json`（Postman Collection v2.1 格式，
  Apifox 原生支持导入），目录与本文档 §4 的编号一一对应；
- 环境文件：`apifox/FinRAG-environment.json`，或在 Apifox「环境管理」中手工新建；
- 环境变量：`base_url`、`token`、`kb_id`、`document_id`、`task_no`、
  `knowledge_point_id`、`message_id`、`session_no`、`batch_no`；
- 内置脚本（`pm.*` API，Apifox 完全兼容，无需改写）：
  - 集合级前置脚本自动附加 `Authorization: Bearer {{token}}` 与 `X-Request-ID`；
  - 登录后自动写入 `token`；上传后写入 `document_id`/`task_no`；
    建知识点后写入 `knowledge_point_id`；问答后写入 `message_id`/`session_no`；
  - 集合级后置脚本对 JSON 响应断言统一结构与 `code == 0`
    （对文件下载与 SSE 响应自动跳过，由各自请求的脚本断言）；
  - 失败场景断言预期错误码（40010 / 40020 / 40100 / 40103 / 50040 等）；
  - `pm.response.responseTime` 用于单请求时延断言（NFR-01/02 的辅助证据）。
- **长期方案**：后端就绪后在 Apifox「项目设置 → 导入数据（自动同步）」中配置
  `http://localhost:8000/openapi.json`（FastAPI 自动生成），并以「智能合并」保留
  已维护的中文名与断言脚本，实现接口文档零维护。

### 7.2 pytest

后端自身的接口契约由 `backend/tests/integration/` 下的 pytest 用例保证，
与 Apifox 集合互为补充：pytest 跑在 CI 里、可断言数据库副作用；
Apifox 用于人工联调、Mock 与全链路测试场景。

### 7.3 职责边界

- Apifox / pytest：接口连通性、契约正确性、错误码、**单请求**时延；
- `scripts/eval_rag.py`：**批量准确率**（110 题评测集）；
- `scripts/bench_api.py`：**分位数时延**（100 次采样，P50/P95/P99）。

详见 `docs/09`。
