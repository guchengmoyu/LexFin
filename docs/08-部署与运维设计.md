# 08 · 部署与运维设计

> 目标：**在一台干净的机器上，`docker compose up -d` 之后全栈可用**（NFR-13），
> 不依赖本地安装 Python、Node、MySQL、Milvus、Tesseract。

**网络**：全部容器接入自定义桥接网络 `finrag-net`，容器间用**服务名**互访
（`mysql:3306`、`milvus:19530`），只有前端与后端对宿主机暴露端口。

## 2. 环境要求

| 项 | 最低 | 建议 |
| --- | --- | --- |
| CPU | 4 核 | 8 核（Embedding 与 OCR 都是 CPU 密集） |
| 内存 | 8 GB | 16 GB（Milvus 约 2GB + MySQL 约 1GB + 后端含模型约 2.5GB） |
| 磁盘 | 20 GB | 40 GB（镜像约 6GB，模型约 1.3GB，数据 < 1GB） |
| 操作系统 | Windows 10/11 + WSL2、Ubuntu 20.04+、macOS | Linux 服务器 |
| Docker | Engine 24+ / Compose v2 | 最新稳定版 |
| 网络 | 可拉取 Docker Hub 镜像；可访问 LLM API | 国内环境建议配置镜像加速 |
| GPU | **不需要** | 有 GPU 时把 `EMBEDDING_DEVICE` 改为 `cuda` 可提速 5~10 倍 |

**首次部署耗时参考**：拉镜像 5~15 分钟（取决于网络）+ 构建后端 3~5 分钟 +
首次启动下载 bge 模型 1~3 分钟 ≈ **15~25 分钟**。

## 3. 目录与卷规划

```
deploy/
├── docker-compose.yml            # 全栈编排（目标状态）
├── docker-compose.infra.yml      # 仅基础设施（立即可用）
├── .env                          # 实际环境变量（不提交 Git）
├── .env.example                  # 模板
├── mysql/init/01-schema.sql      # 首次启动自动执行的建库建表脚本
├── data/                         # ← 业务数据卷（必须备份）
│   ├── uploads/                  #   原始文档，按 yyyyMM 分目录
│   ├── ocr_cache/                #   OCR 结果缓存，按文件 MD5 分目录
│   ├── models/                   #   嵌入模型权重（HF_HOME）
│   └── logs/                     #   应用日志
└── volumes/                      # ← 中间件数据卷（必须备份）
    ├── mysql/                    #   MySQL 数据文件
    ├── milvus/                   #   Milvus 数据（可由 MySQL 重建，备份优先级低）
    ├── etcd/                     #   Milvus 元数据
    └── minio/                    #   Milvus 对象存储
```

> **可重建性分级**（决定备份优先级）：
> `data/uploads` + `volumes/mysql` = **必须备份**（不可再生）；
> `data/models` = 可重新下载（可选备份，离线环境必须备份）；
> `volumes/milvus` + `volumes/etcd` + `volumes/minio` = **可完全重建**
> （`scripts/reindex_all.py` 从 MySQL 重放），备份优先级最低。

**`.gitignore` 必须包含**：`.env`、`data/`、`volumes/`、`__pycache__/`、`node_modules/`、`dist/`。

## 4. 部署流程

### 4.1 阶段一：只想先跑基础设施（**现在就能做**）

```bash
cd deploy
cp .env.example .env
# 至少改：MYSQL_ROOT_PASSWORD、MYSQL_PASSWORD（其余可保持默认）
docker compose -f docker-compose.infra.yml up -d
docker compose -f docker-compose.infra.yml ps      # 等待 healthy
```

验证：

```bash
# MySQL：应看到 16 张表与 v_kb_overview 视图，以及 3 条知识库记录
docker exec -it finrag-mysql mysql -ufinrag -p -e "USE finrag; SHOW TABLES; SELECT code,name FROM knowledge_base;"

# 验证中文全文索引可用（ngram 分词）
docker exec -it finrag-mysql mysql -ufinrag -p -e \
  "USE finrag; SELECT COUNT(*) FROM document_chunk WHERE MATCH(content) AGAINST('流动性风险' IN NATURAL LANGUAGE MODE);"

# Milvus：健康检查
curl -f http://localhost:9091/healthz
# 可视化：浏览器打开 http://localhost:3000（Attu）
```

之后本地开发后端时，`.env` 中把 `MYSQL_HOST` / `MILVUS_HOST` 改为 `127.0.0.1`。

### 4.2 阶段二：全栈一键部署（backend/ 与 frontend/ 就绪后）

```bash
cd deploy
cp .env.example .env
# 【必须修改】SECRET_KEY、MYSQL_*、LLM_API_KEY
docker compose up -d --build
docker compose logs -f backend      # 观察启动日志与建集合结果
```

启动完成后：

| 入口 | 地址 |
| --- | --- |
| 系统界面 | http://localhost:8080 |
| 接口文档（Swagger） | http://localhost:8000/docs |
| 健康检查 | http://localhost:8000/api/v1/health |
| Milvus 控制台（可选） | http://localhost:3000 |

默认管理员：`admin / Admin@123`（由 `SEED_ADMIN_PASSWORD` 决定，**首次登录后必须修改**）。

### 4.3 常用运维命令

```bash
docker compose ps                          # 查看状态与健康
docker compose logs -f --tail=200 backend  # 跟踪后端日志
docker compose restart backend             # 重启单个服务
docker compose up -d --build backend       # 只重建后端
docker compose exec backend bash           # 进入容器排查
docker compose exec backend python -m app.db.init_milvus     # 手动初始化向量集合
docker compose exec backend python -m app.db.seed            # 手动执行种子数据
docker compose exec backend python scripts/reindex_all.py     # 全量重建向量索引
docker compose down                        # 停止（保留数据）
docker compose down -v                     # ⚠ 停止并删除具名卷（数据丢失！）
```

> **警告**：`docker compose down -v` 会删除 `volumes/` 下的数据卷。绑定挂载的 `./volumes/mysql`
> 目录不会被 compose 删除，但仍建议执行前先做一次 `bash scripts/backup.sh`。

## 5. 镜像构建设计

### 5.1 `backend/Dockerfile`

```dockerfile
FROM python:3.11-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    TZ=Asia/Shanghai \
    HF_HOME=/data/models

# 支持解析 .doc 时置为 true（额外安装 LibreOffice，镜像增大约 500MB）
ARG WITH_LIBREOFFICE=false

RUN apt-get update && apt-get install -y --no-install-recommends \
        tesseract-ocr \
        tesseract-ocr-chi-sim \
        tesseract-ocr-eng \
        libgl1 \
        libglib2.0-0 \
        curl \
        tzdata \
    && if [ "$WITH_LIBREOFFICE" = "true" ]; then \
         apt-get install -y --no-install-recommends libreoffice-writer fonts-wqy-zenhei; \
       fi \
    && ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# 依赖层单独缓存：只要 requirements.txt 不变，改代码不会重装依赖
COPY requirements.txt requirements-dev.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN mkdir -p /data/uploads /data/ocr_cache /data/models /data/logs

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=10s --start-period=90s --retries=5 \
    CMD curl -fsS http://localhost:8000/api/v1/health || exit 1

# 单 worker：入库任务用 FastAPI BackgroundTasks 在进程内执行（ADR-06），
# 多 worker 会导致任务重复与内存中状态不一致。水平扩展需先引入消息队列。
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--workers", "1", "--proxy-headers", "--forwarded-allow-ips", "*"]
```

**关键点**

| 点 | 原因 |
| --- | --- |
| `tesseract-ocr-chi-sim` | 中文 OCR 语言包，缺了会直接报错，必须显式安装 |
| `libgl1` / `libglib2.0-0` | OpenCV 运行期依赖，缺失时报 `ImportError: libGL.so.1` |
| `HF_HOME=/data/models` | 模型权重落到挂载卷，容器重建不重新下载 |
| 依赖层与代码层分离 | 改代码时复用 pip 缓存，重建从 4 分钟降到 20 秒 |
| `--proxy-headers` | Nginx 反代后正确获取真实客户端 IP（限流按 IP 时必需） |

### 5.2 `frontend/Dockerfile`（多阶段构建）

```dockerfile
# ---------- 构建阶段 ----------
FROM node:20-alpine AS builder
WORKDIR /app
RUN corepack enable

# Vite 环境变量在构建期注入，运行期不可更改
ARG VITE_API_BASE_URL=/api/v1
ARG VITE_APP_TITLE=金融制度知识问答系统
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
ENV VITE_APP_TITLE=$VITE_APP_TITLE

COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

# ---------- 运行阶段 ----------
FROM nginx:1.25-alpine
RUN rm -f /etc/nginx/conf.d/default.conf
COPY nginx.conf /etc/nginx/conf.d/app.conf
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD wget -qO- http://localhost/ >/dev/null || exit 1

CMD ["nginx", "-g", "daemon off;"]
```

### 5.3 `frontend/nginx.conf`

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # SPA history 路由回退：/chat、/documents 等前端路由直达时不能 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://backend:8000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ★★ SSE 必需：关闭一切缓冲，否则流式问答会变成"憋 5 秒一次性吐出"
        proxy_buffering off;
        proxy_cache off;
        proxy_set_header Connection '';
        chunked_transfer_encoding on;

        # 大文件上传与长回答
        client_max_body_size 60m;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    # 静态资源长缓存（文件名带 hash）
    location ~* \.(js|css|woff2?|png|jpe?g|svg|ico)$ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # index.html 不缓存，保证发版后立即生效
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    gzip on;
    gzip_min_length 1k;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;
}
```

> **最常见的部署事故**：忘记 `proxy_buffering off`。现象是接口"能用"，
> 但答案不是逐字出现，而是一次性全部弹出——验收演示时非常明显。

## 6. 环境变量摘要

完整模板见 `deploy/.env.example`。**必须修改**的四类：

| 变量 | 说明 | 不填的后果 |
| --- | --- | --- |
| `SECRET_KEY` | JWT 签名密钥 | 使用默认值 → 任何人可伪造 token |
| `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` | 数据库密码 | compose 启动时报错退出（`${VAR:?}` 强制校验） |
| `LLM_API_KEY` | 大模型密钥 | 检索可用，问答全部返回 `50030` |
| `SEED_ADMIN_PASSWORD` | 初始管理员密码 | 使用 `Admin@123`，存在弱口令风险 |

**配置分层的三条规则**

1. `.env` 是**唯一**配置来源，代码中不得出现裸常量；
2. `docker-compose.yml` 中的 `environment` 只覆盖**容器内拓扑相关**的值
   （`MYSQL_HOST=mysql` 等），业务参数一律走 `env_file`；
3. 运行期可调的参数（检索 Top-K、Prompt 版本等）同时存在于 `system_config` 表，
   **优先级：`system_config`（可运营调整） > `.env`（部署默认值） > 代码默认值**。

## 7. 启动顺序与健康检查

```
etcd (healthy) ──┐
                 ├──▶ milvus (healthy, start_period 120s) ──┐
minio (healthy) ─┘                                          │
                                                            ├──▶ backend ──▶ frontend
mysql (healthy, start_period 40s) ──────────────────────────┘
```

| 服务 | 健康检查命令 | 起始宽限期 | 说明 |
| --- | --- | --- | --- |
| etcd | `etcdctl endpoint health` | 20s | |
| minio | `curl -f localhost:9000/minio/health/live` | 20s | |
| milvus | `curl -f localhost:9091/healthz` | **120s** | 首次启动需初始化存储，最慢 |
| mysql | `mysqladmin ping` | 40s | 首次启动要执行 `01-schema.sql` |
| backend | `curl -fsS localhost:8000/api/v1/health` | 90s | 首次要加载嵌入模型 |
| frontend | `wget -qO- localhost/` | — | |

**后端启动钩子（`app/main.py` 的 `lifespan`）执行顺序**：

```
1. 建立 MySQL 连接池，重试 10 次（间隔 3s）—— 容忍 MySQL 尚未就绪
2. 校验数据库版本与表结构（缺表则打印明确指引）
3. 执行 seed：确保管理员账号存在、三个知识库存在
4. 建立 Milvus 连接，重试 10 次（间隔 5s）
5. 确保集合 finrag_embedding_v1 存在，否则按 docs/03 §3.2 建集合 + 建索引
6. 确保别名 finrag_embedding 指向该集合
7. 加载嵌入模型（首次会下载，日志打印进度）
8. 检查 OCR 可用性（tesseract 可执行 + chi_sim 语言包），失败仅告警不阻断启动
9. 打印启动完成横幅（含版本、模型名、集合实体数、监听地址）
```

**任一必需依赖失败 → 进程退出并打印可操作的中文提示**，而不是带病启动
（例如 `无法连接 MySQL(host=mysql:3306)：请确认容器 finrag-mysql 状态为 healthy`）。

## 8. 数据初始化与重建

| 目标 | 命令 |
| --- | --- |
| 建表 + 初始化知识库 | 首次启动 MySQL 容器自动执行 `mysql/init/01-schema.sql` |

## 9. 备份与恢复

### 9.1 备份（`scripts/backup.sh`）

```bash
#!/usr/bin/env bash
set -euo pipefail
TS=$(date +%Y%m%d_%H%M%S)
DEST="./backups/${TS}"
mkdir -p "$DEST"

# 1. MySQL 逻辑备份（必做）
docker exec finrag-mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction \
     --routines --triggers --default-character-set=utf8mb4 finrag' \
  | gzip > "$DEST/finrag_mysql.sql.gz"

# 2. 原始文档与 OCR 缓存（必做）
tar -czf "$DEST/data.tar.gz" -C ./data uploads ocr_cache

# 3. 环境变量（含密钥，注意保管）
cp .env "$DEST/env.bak"

echo "备份完成：$DEST"
```

> Milvus 数据**不备份**：它是 MySQL 的派生索引，用 `reindex_all.py` 重建比恢复更快更可靠。

**建议频率**：开发期每天一次；答辩前做一次完整备份并**实际演练一次恢复**。

### 9.2 恢复

```bash
# 1. 停应用，保留中间件
docker compose stop backend frontend

# 2. 恢复 MySQL
gunzip -c backups/<TS>/finrag_mysql.sql.gz | \
  docker exec -i finrag-mysql mysql -uroot -p finrag

# 3. 恢复文件
tar -xzf backups/<TS>/data.tar.gz -C ./data

# 4. 重建向量索引（从 MySQL 重放，无需恢复 Milvus 卷）
docker compose exec backend python scripts/reindex_all.py

# 5. 启动
docker compose start backend frontend
```

## 10. 日志与监控

| 项 | 设计 |
| --- | --- |
| 应用日志 | loguru 输出到 stdout（`docker logs`）+ 滚动文件 `/data/logs/app.log`（10MB × 10） |
| 容器日志 | json-file 驱动，`max-size=20m`、`max-file=5`（已在 compose 中配置） |
| 请求日志 | 每请求一行：`method path status duration_ms user_id request_id` |
| 问答链路 | 每轮一行：`session request_id rewrite retrieve rerank llm_ttft total confidence answer_type` |
| 慢请求告警 | 超过 `SLOW_REQUEST_MS`（默认 5000）打 `WARNING`，便于定位性能退化 |
| 健康检查 | `GET /api/v1/health`，可被外部探针或 `scripts/watch_health.sh` 轮询 |
| 指标（P2） | 可挂 `prometheus-fastapi-instrumentator` 暴露 `/metrics`，一期不做 |

## 11. 故障排查手册

| 现象 | 可能原因 | 排查与解决 |
| --- | --- | --- |
| `docker compose up` 报 `必须设置 MYSQL_ROOT_PASSWORD` | `.env` 未创建或未填 | `cp .env.example .env` 并填写 |
| 后端反复重启，日志 `无法连接 MySQL` | MySQL 未 healthy 或密码不一致 | `docker inspect --format '{{.State.Health.Status}}' finrag-mysql`；核对 `.env` 密码与已有数据卷中的旧密码是否一致（改密码后需删 `volumes/mysql` 重建） |
| 后端日志 `连接 Milvus 超时` | Milvus 首次启动慢（> 2 分钟） | 等待并查看 `docker logs finrag-milvus`；确认 etcd 与 minio 都 healthy |
| `GET /health` 中 `ocr: unavailable` | 镜像缺少中文语言包 | `docker exec finrag-backend tesseract --list-langs` 应含 `chi_sim`；确认 Dockerfile 安装了 `tesseract-ocr-chi-sim` |
| 解析时报 `ImportError: libGL.so.1` | 镜像缺 OpenCV 依赖 | Dockerfile 补 `libgl1 libglib2.0-0` 后重新 build |
| 首次启动卡在"加载嵌入模型" | 模型下载慢或被墙 | 设置 `HF_ENDPOINT=https://hf-mirror.com`；或离线把权重放入 `data/models` 并设 `HF_HUB_OFFLINE=1` |
| 问答不流式，一次性全出 | **Nginx 缓冲未关闭** | 确认 `nginx.conf` 有 `proxy_buffering off` 且响应头含 `X-Accel-Buffering: no` |
| 上传大文件返回 413 | Nginx 与后端限制未放开 | `client_max_body_size 60m`；后端 `MAX_FILE_SIZE_MB` 一致 |
| 中文关键词检索零命中 | `ngram_token_size` 与查询词长度不匹配 | 单字查询在 ngram=2 下必然零命中，属预期；确认 `--ngram_token_size=2` 启动参数生效；检查代码走了 `LIKE` 兜底分支 |
| `MATCH ... AGAINST` 报 `Can't find FULLTEXT index` | 表由旧脚本创建，缺 ngram 索引 | 执行 `ALTER TABLE document_chunk ADD FULLTEXT ft_content (content) WITH PARSER ngram;` |
| 提问返回 `50030` | LLM 渠道不可用/欠费/密钥错 | `docker compose exec backend python -c "from app.rag.llm import health_check; print(health_check())"`；检查 `LLM_BASE_URL` 是否含 `/v1` |
| 检索正常但答案总说"未检索到" | `RETRIEVAL_MIN_SCORE` 过高或证据未入库 | 调 `POST /retrieve` 看 `items` 是否为空；查 `SELECT COUNT(*) FROM document_chunk` 与 Milvus 实体数是否一致，跑 `check_consistency.py` |
| 入库任务一直是 `queued` | 后端重启导致后台任务丢失（ADR-06） | 调 `POST /documents/{id}/reparse` 重新入库；生产化需引入消息队列 |
| Milvus 实体数与 MySQL 不一致 | 上次入库在向量化阶段失败 | `python scripts/check_consistency.py --fix` 重新向量化差异切片 |
| 前端刷新后 404 | Nginx 缺 `try_files` 回退 | 检查 `nginx.conf` 的 `try_files $uri $uri/ /index.html` |
| 前端请求 401 后不跳登录 | 拦截器未覆盖该错误码 | 核对 `request.ts` 中的 `[40100,40101,40102]` 分支 |
| 端口被占用 | 本机已装 MySQL 等 | 修改 `.env` 中的 `*_HOST_PORT` 映射到空闲端口 |

## 12. 生产加固建议（超出课设范围，供后续参考）

| 项 | 建议 |
| --- | --- |
| 传输加密 | 前置 HTTPS 终结（Caddy / 云负载均衡），SSE 需确认不启用响应压缩缓冲 |
| 密钥管理 | 用 Docker secrets 或 Vault 替代 `.env` 明文 |
| 数据库账号 | 应用使用最小权限账号（仅 DML + 指定表的 DDL），不用 root |
| 备份自动化 | `cron` 每日执行 `backup.sh` 并同步到异地/对象存储 |
| 水平扩展 | 先引入 Redis（会话/缓存/限流）+ 消息队列（入库任务），再把 uvicorn worker 数调大 |
| 可观测 | 接入 Prometheus + Grafana，采集 QPS、P95 时延、错误率、token 消耗 |
| 安全扫描 | 镜像 `trivy` 扫描、依赖 `pip-audit` / `pnpm audit` |
