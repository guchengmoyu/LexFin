# 09 · 测试方案设计

> 课题明确要求使用 **pytest + 接口调试工具**开展测试。本项目接口测试环节选用 **Apifox**
> （导入方式与自动化用法见 `apifox/README.md`）。本文档定义测试分层、用例清单、
> 性能口径，以及 **85% 准确率指标的完整评测方法**——后者是答辩现场最容易被追问的部分。

## 1. 测试策略

```
                       ┌──────────────────────────────┐
                       │  L4 人工评测（准确率 ≥85%）   │  scripts/eval_rag.py + 双人标注
                       │      110 题 × 2 人            │  产出：验收报告
                       └──────────────────────────────┘
                    ┌────────────────────────────────────┐
                    │  L3 性能测试（时延/并发）           │  scripts/bench_api.py + Locust
                    │      检索 P95≤500ms / TTFT≤2s      │
                    └────────────────────────────────────┘
                 ┌──────────────────────────────────────────┐
                 │  L2 接口测试（pytest + Apifox）           │  ~120 用例
                 │      覆盖全部 REST 接口与错误码           │
                 └──────────────────────────────────────────┘
              ┌────────────────────────────────────────────────┐
              │  L1 单元测试（pytest）                          │  ~90 用例
              │      parser / chunker / rrf / prompt / citation │
              │      / scorer / security / schemas              │
              └────────────────────────────────────────────────┘
```

| 层次 | 工具 | 运行时机 | 目标 |
| --- | --- | --- | --- |
| L1 单元 | pytest | 每次提交 | 核心算法与纯函数正确；覆盖率 ≥ 70%（核心模块） |
| L2 接口 | pytest + httpx；**Apifox**（调试、Mock、测试场景、CLI） | 每日 / 联调后 | 全部接口按契约工作，错误码正确 |
| L3 性能 | `bench_api.py`、Locust | 每周 / 验收前 | NFR-01~04 达标 |
| L4 评测 | `eval_rag.py` + 人工标注 | 每次 Prompt/检索变更后 + 验收前 | **准确率 ≥ 85%**（NFR-06） |

## 2. 测试环境

| 项 | 配置 |
| --- | --- |
| L1 单元测试 | 无需外部依赖，全部 mock；`pytest -m unit` 应在 30 秒内跑完 |
| L2 接口测试 | 需要真实 MySQL + Milvus（用 `docker-compose.infra.yml` 起）；LLM 与 Embedding 用 Fake 实现 |
| L3 性能测试 | 完整栈（含真实 LLM），单机 Docker，与生产同配置 |
| L4 人工评测 | 完整栈 + 真实 LLM；评测集题面**不得**出现在 Prompt 或文档标题中，避免泄漏 |
| 测试数据 | 从公开渠道下载的银行/证券/保险制度文件，另存为固定 `tests/fixtures/` 小样本 |

### 3.2 关键 fixture

```python
# tests/conftest.py
import pytest, hashlib
from httpx import AsyncClient, ASGITransport
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from app.main import app
from app.core.deps import get_db
from app.rag.embedder import get_embedder
from app.rag.llm import get_llm

# ---- 确定性 Fake Embedding：测试快、可复现，且语义相近的文本向量相近 ----
class FakeEmbedder:
    dim = 1024
    def encode(self, texts: list[str]) -> list[list[float]]:
        vecs = []
        for t in texts:
            seed = int(hashlib.md5(t.encode()).hexdigest()[:8], 16)
            # 用字符 n-gram 的哈希构建伪语义向量：相同/相近文本得到相近向量
            v = [0.0] * self.dim
            for i, ch in enumerate(t):
                v[(ord(ch) + i) % self.dim] += 1.0
            norm = sum(x * x for x in v) ** 0.5 or 1.0
            vecs.append([x / norm for x in v])
        return vecs

# ---- 确定性 Fake LLM：按上下文编号输出带角标的答案 ----
class FakeLLM:
    def __init__(self, answer: str | None = None):
        self.answer = answer or "根据参考条文，该指标应当不低于100%[1]。"
    async def astream(self, messages, **kw):
        for ch in self.answer:
            yield ch
    async def ainvoke(self, messages, **kw):
        return self.answer

@pytest.fixture
def fake_embedder(monkeypatch):

    monkeypatch.setattr("app.rag.embedder.get_embedder", lambda: fake)
    return fake

@pytest.fixture
def fake_llm(monkeypatch):
    fake = FakeLLM()
    monkeypatch.setattr("app.rag.llm.get_llm", lambda **kw: fake)
    return fake

# ---- 数据库：每个用例一个事务，结束后回滚，互不污染 ----
@pytest.fixture
def db_session(engine):
    conn = engine.connect()
    tx = conn.begin()
    Session = sessionmaker(bind=conn)

# ---- API 客户端：直接挂 ASGI，不走网络 ----
```

| --- | --- |

**集合级前置脚本**（自动带上 token 与链路追踪头）

```javascript
const token = pm.environment.get('token');
if (token) { pm.request.headers.upsert({ key: 'Authorization', value: 'Bearer ' + token }); }
pm.request.headers.upsert({
    key: 'X-Request-ID',
    value: 'af-' + Date.now().toString(36) + Math.random().toString(36).slice(2, 8)
});
```

**集合级后置脚本**（对 JSON 响应统一断言，二进制与 SSE 自动跳过）

```javascript
pm.test('HTTP 状态码在 2xx', function () { pm.response.to.be.success; });
const ct = pm.response.headers.get('Content-Type') || '';
if (ct.includes('application/json')) {
    pm.test('响应体符合统一结构（code/message/request_id）', function () {
        const b = pm.response.json();
        pm.expect(b).to.have.property('code');
        pm.expect(b).to.have.property('message');
        pm.expect(b).to.have.property('request_id');
        pm.expect(b.code).to.eql(0);
    });
}
```

**登录请求的后置脚本**（写入 token，是整条链路的起点）

```javascript
pm.test('登录成功且返回 token', function () {
    const d = pm.response.json().data;
    pm.expect(d.access_token).to.be.a('string').and.not.empty;
    pm.expect(d.user.role).to.be.oneOf(['admin', 'editor', 'viewer']);
    pm.environment.set('token', d.access_token);
});
pm.test('响应体不含密码哈希', function () {
    pm.expect(pm.response.text()).to.not.include('password_hash');
});
pm.test('登录耗时 < 1000ms', function () {
    pm.expect(pm.response.responseTime).to.be.below(1000);
});
```

**问答请求的后置脚本**（绕不开的核心断言：答案必须有可回溯的角标）

```javascript
const d = pm.response.json().data;
pm.test('正常回答必须带引用且在答案中可找回角标', function () {
    if (d.answer_type === 'answered') {
        pm.expect(d.citations.length).to.be.above(0);
        d.citations.forEach(function (c) {
            pm.expect(d.answer, '答案缺少角标 [' + c.cite_index + ']')
              .to.include('[' + c.cite_index + ']');
        });
    }
});
pm.test('拒答时不得编造内容', function () {
    if (d.answer_type === 'refused') { pm.expect(d.answer).to.include('未检索到'); }
});
pm.environment.set('message_id', d.message_id);
pm.environment.set('session_no', d.session_no);
```

## 5. L3 性能测试

### 5.1 响应时间口径（★ 必须先定义清楚，否则 2 秒无法验收）

| 编号 | 指标名 | 精确定义 | 目标 |
| --- | --- | --- | --- |
| **T1** | 检索响应时间 | `POST /retrieve` 或 `GET /search`：从发出请求到**完整接收响应体**的耗时 | **P95 ≤ 500 ms**，P50 ≤ 300 ms |
| **T2** | 问答首字节时间（TTFT） | `POST /qa/ask/stream`：从发出请求到收到**第一个 SSE 事件**（`meta` 或首个 `token`，取先到者）的耗时 | **P95 ≤ 2000 ms**，P50 ≤ 1500 ms |
| **T3** | 问答完整响应时间 | 到收到 `done` 事件的耗时（含 LLM 生成完整答案） | 参考值 P95 ≤ 8 s（**不作为硬性验收指标**） |
| **T4** | 文档入库耗时 | 单份 ≤ 50 页 PDF：任务从 `queued` 到 `success` | ≤ 90 s |

**测量条件**（三者必须同时满足，报告中必须写明）

1. 单机 Docker 全栈部署，与生产同配置；
2. **单请求串行**，无并发（T1~T3）；预热 5 次后连续测量 **100 次**；
3. 客户端与服务器同机（localhost），排除公网抖动——**T2 包含外部 LLM 的真实首 token 时间**。

> **关于「系统响应时间不超过 2 秒」的说明（必须写进验收报告）**
>
> 本系统采用流式输出，用户**在 2 秒内即可看到答案开始逐字出现**并同时看到引用条文列表，
> 这满足 T2 口径。若按最严格的「完整答案 ≤ 2 秒」口径，则取决于外部大模型的生成速度
> （`deepseek-chat` 生成 300 字约需 3~6 秒），单靠应用层无法保证。
>
> **达标措施（按优先级）**：
> 1. **主口径采用 T2**（首字节/首 token），这是 LLM 应用的行业通用口径；
> 2. 若答辩方坚持端到端 ≤ 2s，则启用：`LLM_MAX_TOKENS=300` +
>    切换 `qwen-turbo` 等低延迟模型 + 高频 Top-100 问题答案缓存（Redis）；
> 3. 无论口径如何，**T1 检索响应 P95 ≤ 500ms 始终可达标**，这是纯自研部分的能力证明。

### 6.1 评测集设计

| 项 | 要求 |
| --- | --- |
| 题目总数 | **110 题**（100 道可回答题 + 10 道**知识库外**题用于验证拒答） |
| 分类分布 | 银行 45 / 证券 30 / 保险 25（可回答题部分） |
| 题型分布 | 数值型 30 / 条件型 25 / 定义型 20 / 流程型 15 / 关联跨制度型 10 |
| 难度分布 | 1 基础 50 / 2 进阶 35 / 3 专家 15 |
| 答案来源 | 每题的「标准答案要点」必须从制度原文中摘取，标注 `doc_no` + `article_no` |
| 防泄漏 | 题面不得与文档标题、知识点标题**逐字相同**；出题人不得是同一人 |
| 存储 | `data/eval/eval_set.xlsx` |

**评测集字段**

| 列 | 说明 |
| --- | --- |
| `qid` | 题目编号 `Q001` |
| `category` | `banking` / `securities` / `insurance` / `out_of_scope` |

| `question_type` | 数值型 / 条件型 / 定义型 / 流程型 / 关联型 |

### 6.2 人工判分规范（★ 准确率能否被认可的关键）

一道题判为**「正确」必须同时满足以下 4 条**，任一条不满足即判**错误**：

| # | 判据 | 判定方法 |
| --- | --- | --- |
| 1 | **事实正确** | 答案中的数值、比例、金额、期限、主体、条件与制度原文**逐一致**，无虚构内容 |
| 2 | **要点完整** | 覆盖 `expected_key_points` 的 **≥ 80%** |
| 3 | **溯源有效** | 至少 1 个引用角标，且被引条文**确实支撑**该结论（引用错条也判错） |
| 4 | **时效无误** | 未把已废止/已修订条文当作现行有效陈述 |

错误时**必须**打上 `error_type`：

| error_type | 含义 |
| --- | --- |
| `retrieval_miss` | 相关条文未召回，导致答非所问（检索问题） |
| `hallucination` | 答案含原文中不存在的内容（生成问题） |
| `citation_wrong` | 引用角标指向的条文不支持该结论（溯源问题） |
| `outdated` | 引用了已废止条文且未提示（时效问题） |
| `incomplete` | 要点覆盖 < 80%（召回或上下文裁剪问题） |

**判分流程**

```
1. 脚本跑出全部 110 题的答案，导出为 answers_<batch>.xlsx（含 question/answer/citations）
2. 两名标注人（不知对方结果）各自独立判分
3. 计算 Cohen's Kappa：
      κ >= 0.8  高度一致 → 直接采用
      0.6 <= κ < 0.8  中等 → 由第三方裁决分歧项
      κ < 0.6  一致性不足 → 重新培训并重判（说明判分标准有歧义）
4. 分歧项由第三人（企业导师或指导老师）裁决
5. 最终准确率 = 判为 correct 的题数 / 100（**分母不含 10 道拒答题**）
6. 拒答正确率单独统计 = 正确拒答的题数 / 10
```

### 6.4 不达标时的调优路径（按 ROI 排序）

| 顺序 | 手段 | 预期提升 | 代价 |
| --- | --- | --- | --- |
| 1 | 检查 `retrieval_miss` 集中题型，补充相应文档或知识点 | +3~8% | 数据工作量 |
| 2 | 调整 RRF 权重（网格搜索 0.5/0.5 ~ 0.8/0.2） | +2~5% | 无 |
| 3 | 启用重排模型 `bge-reranker-base` | +3~7% | P95 +150~300ms |
| 4 | 优化 Chunker 正则（提升条号识别率） | +2~5% | 需重新入库 |
| 5 | Prompt 迭代（编号方式、规则措辞、few-shot） | +3~10% | 需回归验证 |
| 6 | 增大 `FINAL_TOP_N` 到 8 并放宽上下文预算 | +2~4% | TTFT +100~300ms |
| 7 | 对高频错误题型补充 `same_topic` 关联知识点 | +1~3% | 数据工作量 |
