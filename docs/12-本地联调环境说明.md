# 12 本地前后端联调环境说明（Dev Mode）

> 目的：把「基础设施（MySQL / Milvus）+ FastAPI 后端 + Vue3 前端」在本机跑起来，
> 前端通过 Vite 开发服务器代理 `/api` 到后端，完成接口级联调。
> 生产形态（Nginx + 容器全栈）见 `docs/08`，本文只覆盖开发联调。

---

## 一、端口规划（本地联调）

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| 前端（Vite dev） | <http://localhost:5173> | `proxy /api → http://127.0.0.1:8002`（端口取 `LEXFIN_BACKEND_PORT`） |
| 后端（uvicorn） | <http://127.0.0.1:8002> | Swagger：`/docs`，健康检查：`/api/v1/health` |
| MySQL 8.0 | `127.0.0.1:3307` | 容器 `finrag-mysql`（**3306 被本机 MySQL80 服务占用**，故映射到 3307） |
| Milvus 2.4 | `127.0.0.1:19530` | 容器 `finrag-milvus`，指标端口 9091 |
| MinIO | `127.0.0.1:9000` / 控制台 `9001` | MinIO 控制台账号 `minioadmin / minioadmin` |
| etcd | 容器内部 2379 | Milvus 元数据 |
| Attu | <http://localhost:3000> | Milvus 可视化管理台 |

> 后端默认端口选 **8002**：本机 **8000、8001 都曾被历史（且跨会话不可终止的）uvicorn 进程占用**，
> 换端口是最省事的规避方式。端口是统一的：
> `scripts/dev-start.ps1 -BackendPort N` 会设置 `LEXFIN_BACKEND_PORT=N`，
> 而 `frontend/vite.config.js` 读取该变量作为 proxy target，所以只改参数即可。
> 若 8002 也被占用，换一个空闲端口并同样传 `-BackendPort`。
>
> 清理旧进程（在**管理员** PowerShell 中执行，需先 `netstat -ano | findstr :8000` 查到 PID）：
> `Stop-Process -Id <PID> -Force`；普通权限下这些跨会话进程可能杀不掉。

## 三、一键启动 / 停止

```powershell
# 启动（基础设施 + 后端 + 前端，含探活）
pwsh -File scripts/dev-start.ps1

# 只重启应用进程（基础设施已在运行）
pwsh -File scripts/dev-start.ps1 -SkipInfra

# 停止应用进程（保留 Docker 容器）
pwsh -File scripts/dev-stop.ps1

# 连基础设施一起停
pwsh -File scripts/dev-stop.ps1 -IncludeInfra
```

日志：`logs/backend.out.log`、`logs/backend.err.log`、`logs/frontend.out.log`、`logs/frontend.err.log`。

等价的手工命令：

```powershell
# 1) 基础设施
cd deploy
docker compose -f docker-compose.infra.yml up -d
docker compose -f docker-compose.infra.yml ps     # 等 mysql / milvus 都是 healthy

# 2) 后端（backend 目录，加载 backend/.env）
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8002 --reload --reload-dir app

# 3) 前端（frontend 目录）
npm run dev
```

> 注意：Docker CLI、`uvicorn --reload`、esbuild 都依赖 Windows 命名管道，
> 必须在**普通 PowerShell 窗口**执行；在受限沙箱环境会报
> `permission denied ... npipe` 或 `spawn EPERM`。

## 七、已知限制与下一步

1. **LLM 仍是 FakeLLM**：回答固定为「根据参考条文，该指标应当不低于100%[1]」。
   在 `backend/.env` 填入 `LLM_API_KEY`，把 `LLM_PROVIDER` 改为 `openai_compatible`，重启后即走真实 DeepSeek
   （**详细步骤、其他厂商与本地 Ollama 见 §9**，验证用 `scripts/check_llm.ps1`）。
2. **Embedding 是伪向量**：`EMBEDDING_PROVIDER=fake` 只能验证链路，语义检索结果无意义。
   切回 `local` 会首次下载 `BAAI/bge-large-zh-v1.5`（约 1.3GB）；
   切换后需用 `python scripts/reindex_all.py` 重建已有切片向量，否则查询向量与入库向量不同源。
3. **知识点批量导入依赖原文先入库**：导入会按 `source_file` 精确匹配已 `ready` 的文档、
   并要求 `quote_text` 在切片中唯一命中（`app/services/knowledge_point.py:_resolve_import_source`）。
   仓库内 `data/knowledge_points/knowledge_points_candidates.xlsx` 引用的 `banking_*.docx` 尚未上传，
   因此 dry_run 结果是「来源文件未入库或版本不唯一」——属于**数据依赖**，不是缺陷。
   达标路径：先上传 3 个知识库对应的制度原文 → 再导入候选知识点。
4. **前端生产镜像缺失**：`frontend/` 目前只有 Vite 工程，没有 `Dockerfile` + `nginx.conf`，
   所以 `docker compose up` 的全栈模式还起不来（联调用 `npm run dev`）。
5. **UI 人工点检**：本次通过「Vite 编译 + 接口实测」验证契约；建议打开
   <http://localhost:5173> 走一遍：登录 → 文档上传/切片预览 → 问答流式出字与角标 → 收藏 → 知识点审核。
6. **8000 端口遗留进程**：若在任务管理器里看到旧的 `python.exe` 占用 8000，结束它之后
   可改回 8000（`-BackendPort 8000` + 同步 vite proxy）。

## 九、切换到真实 LLM（联调收尾必做）

代码里只有一处开关：`app/rag/llm.py:get_llm()`

```python
if (settings.llm_provider or "").lower() == "fake":     # 联调占位
    return FakeLLM()
return LLMClient()                                      # OpenAI 兼容协议（DeepSeek/通义/智谱/Kimi/Ollama）
```

所以切换真实模型**不需要改代码**，只改 `backend/.env` 后重启。

### 9.1 方案 A：DeepSeek（推荐，中文金融语料表现好、价格低）

1. 注册 <https://platform.deepseek.com> → 「API keys」→ 创建 Key（`sk-` 开头，只显示一次）。
2. 编辑 `backend/.env`：

```ini
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_API_KEY=sk-你的真实key
LLM_MODEL=deepseek-chat          # 需要推理链可换 deepseek-reasoner
LLM_TEMPERATURE=0.1
LLM_MAX_TOKENS=800
LLM_TIMEOUT=20
LLM_TTFT_TIMEOUT=5
```

3. 重启后端（`--reload` 对整文件替换不一定生效，直接重启最稳）：

```powershell
pwsh -File scripts/dev-stop.ps1
pwsh -File scripts/dev-start.ps1 -SkipInfra
```

4. 一键验证：

```powershell
pwsh -File scripts/check_llm.ps1
```

期望输出：

```
LLM：provider=openai_compatible model=deepseek-chat status=ok
模型      : deepseek-chat
tokens    : prompt=1180 completion=96 total=1276
结论：已接真实大模型，链路正常。
```

若显示 `模型: fake-llm` / 退出码 2 → 仍是占位实现（Key 没生效或后端没重启）；
若报 `50030 大模型服务暂时不可用` → Key 无效、余额不足、`LLM_BASE_URL` 不通，
或后端跑在**无外网的受限环境**里。

### 9.2 方案 B：其他 OpenAI 兼容厂商（只改三行）

| 厂商 | `LLM_BASE_URL` | `LLM_MODEL` 示例 |
| --- | --- | --- |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 通义千问（DashScope 兼容模式） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus` |
| 月之暗面 Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |

**备用渠道**（主渠道失败/超时自动降级一次，代码见 `LLMClient._chain`）：

```ini
LLM_FALLBACK_ENABLED=true
LLM_FALLBACK_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_FALLBACK_API_KEY=sk-通义的key
LLM_FALLBACK_MODEL=qwen-plus
```

### 9.3 方案 C：本地 Ollama（零调用成本，演示/离线可用）

```powershell
# 安装 Ollama 后
ollama pull qwen2.5:7b          # 约 4.7GB
```

`backend/.env`：

```ini
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_API_KEY=ollama              # 任意非空字符串
LLM_MODEL=qwen2.5:7b
LLM_TIMEOUT=120                 # 本地模型首 token 慢，适当放大
LLM_TTFT_TIMEOUT=30
```

> 注意：本地 7B 模型首 token 常见 5~20s，会**超出「≤2 秒」验收红线**，
> 适合功能联调和离线演示，不适合性能验收；性能验收仍应用云 API。

### 9.4 切换后必须知道的几点

1. **token 用量与预算**：`qa_message.token_usage` 会记录真实用量；
   `LLM_DAILY_TOKEN_BUDGET=2000000` 为当日预算保护。一次问答典型 1k~3k tokens。
2. **仍有拒答分支**：Top-1 融合分 < `RETRIEVAL_MIN_SCORE`（默认 0.30）时不调 LLM，
   直接返回标准拒答话术。当前 embedding 仍是 fake、融合分偏低容易触发拒答；
   要问答效果正常，按 §7-2 切 `local` 向量并 `python scripts/reindex_all.py` 重建。
3. **密钥安全**：`backend/.env` 已在 `.gitignore`，不会提交；团队协作各自配本地 Key，
   不要写进代码或文档。
4. **端到端检查点**：`/health` → `scripts/check_llm.ps1` → 前端问答页看流式出字 + 角标 +
   `done.model_name`。

## 十、真实数据入库（原文 → 知识点）

### 10.1 顺序不能反

```
original/*.pdf  ──上传──▶ document(ready) + document_chunk ──┐
                                                             ├─▶ knowledge_point_source（溯源）
data/…/knowledge_points_*.xlsx ──导入──▶ knowledge_point ────┘
```

- `knowledge_point` 导入要求 `source_file` 与 `documents.file_name` **完全一致**，
  且 `quote_text` 能在该文档切片中定位，所以**必须先上传原文再导知识点**。
- 上传后 `status` 必须是 `ready`（`parsing/embedding` 都匹配不到）。

### 10.2 两条命令

```powershell
cd backend

# ① 按 document_registry 批量上传原文（7s 间隔，避开 10 次/分钟限流）
.\.venv\Scripts\python.exe -m scripts.upload_member2_docs --registry ..\.tmp_reg\registry.xlsx

# ② 导知识点（先 dry-run 看校验，再真导入 + 发布）
.\.venv\Scripts\python.exe -m scripts.import_member2_kp --dry-run --category banking
.\.venv\Scripts\python.exe -m scripts.import_member2_kp --publish
```

> `--publish` 必须加：关键词通道 SQL 与合并后过滤都要求
> `status=published AND verify_status=passed`，否则「导了但搜不到」。

### 10.3 脚本解决的两个真实差异

| 差异 | 原因 | 处理 |
| --- | --- | --- |
| registry 里 5 份写 `.docx`，实际是 `.pdf` | 原文下载格式不同 | 导入前按「同名不同扩展」改写 `source_file`，并统计「库中缺失」 |
| 引用匹配失败（0 个 / 多个切片） | 长引用跨 2~3 个切片；相邻切片 80 字重叠导致重复命中 | `_resolve_import_source` 增加三级兜底：跨窗口匹配 → 前 120 字定位 → 条号唯一定位（均要求唯一） |

### 10.4 数据口径

- 候选表 1228 行 → 剔除 3 行标题非法（抽取残留的「其中」）→ **1225 行可导入**
- `securities` 新增子分类字典值 `证券发行交易与监管`（成员2 审核批次的合并类目，已同步 docs/03 §4.2）
- 导入后 `coverage_rate=1.0`（每条 KP 都绑定了来源切片），`without_source=0`

### 10.5 性能

逐条向量化约 3.9s/条；`import_file(..., defer_embedding=True)` 改为最后按 64 条/批向量化，
464 条约 8.5 分钟（嵌入占绝大部分）。全量 1225 条约 20~25 分钟。
