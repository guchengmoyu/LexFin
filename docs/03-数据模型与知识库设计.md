# 03 · 数据模型与知识库设计

> 本文档是**开发契约**。表结构、字段名、枚举值以本文档与 `deploy/mysql/init/01-schema.sql` 为准，
> 代码中通过 ORM 映射，禁止自行增删字段而不更新本文档。

## 1. 存储分工

| 存储 | 存什么 | 不存什么 |
| --- | --- | --- |
| **MySQL 8.0** | 用户、知识库、文档元数据、切片正文、知识点、问答会话/消息/引用、收藏、反馈、校验记录、入库任务 | 向量数据 |
| **Milvus 2.4** | 切片与知识点的向量 + 用于过滤的标量字段 + 正文冗余副本 | 用户数据、会话数据 |
| **本地文件卷 `/data`** | 原始上传文件、OCR 中间产物、本地嵌入模型权重 | 数据库文件（由各自容器卷管理） |

**一致性原则**：MySQL 为**唯一事实来源**；Milvus 是可由 MySQL 重建的**派生索引**。
任何时候只要 `document_chunk` 与 `knowledge_point` 还在，跑一次 `scripts/reindex_all.py` 就能恢复向量库。

## 2. MySQL 表结构

### 2.0 ER 总览

```
 knowledge_base 1─┬─* document 1───* document_chunk
                  │                      │  ▲
                  └─* knowledge_point *──┘  │ (knowledge_point_source 多对多)
                           │  │
                           │  └─* knowledge_point_relation
                           │
 user 1─┬─* qa_session 1─* qa_message 1─* qa_citation ──▶ (document/chunk/kp 弱引用)
        ├─* favorite ──▶ qa_message
        ├─* qa_feedback ──▶ qa_message
        ├─* qa_review (target: answer | knowledge_point)
        └─* ingest_task ──▶ document
        └─* operation_log

```

> `qa_citation` 对 document/chunk/kp 是**弱引用且字段冗余**：即使原文档被删除，
> 历史问答的溯源信息仍可完整展示。

```sql
FROM qa_review
WHERE target_type = 'answer'
GROUP BY batch_no;
```

## 3. Milvus 集合设计

### 3.1 集合与别名

| 项 | 值 |
| --- | --- |
| 集合名 | `finrag_embedding_v1` |
| 别名 | `finrag_embedding`（**代码只使用别名**，便于零停机重建索引） |
| 用途 | 同时存放 `chunk` 与 `knowledge_point` 两类实体的向量，用 `source_type` 区分 |
| 预估规模 | 切片 2~4 万 + 知识点 1000 ≈ **5 万条以内**，单机 standalone 轻松承载 |

### 3.2 Schema

| 字段 | 类型 | 属性 | 说明 |
| --- | --- | --- | --- |
| `pk` | VARCHAR(64) | **主键**，auto_id=False | `chunk_{id}` 或 `kp_{id}`，全局唯一且可读 |
| `embedding` | FLOAT_VECTOR | dim=**1024** | 归一化后写入，使用 COSINE 度量 |
| `source_type` | VARCHAR(16) | | `chunk` / `knowledge_point` |
| `source_id` | INT64 | | 对应 MySQL 表主键 |
| `kb_id` | INT64 | | 过滤用 |
| `document_id` | INT64 | | 删除/重建用；知识点取 `primary_document_id`，无则 0 |
| `category` | VARCHAR(32) | | `banking` / `securities` / `insurance` |
| `timeliness` | VARCHAR(16) | | 时效过滤 |
| `article_no` | VARCHAR(32) | | 回显；超过 32 UTF-8 字节的条款范围在 Milvus 中留空，完整值保留在 MySQL 与正文 |
| `page_no` | INT32 | | 回显 |
| `chunk_index` | INT32 | | 切片顺序，用于上下文扩展（取相邻块） |
| `publish_year` | INT32 | | 年份过滤（如「只看 2020 年后」） |
| `content` | VARCHAR(8192) | | 正文冗余副本，**命中后免回表 MySQL**，直接组装 Prompt |

> `content` 冗余是本设计满足 NFR-01/02 的关键手段之一：检索到 Top-5 后无需再查 MySQL 即可拼 Prompt，
> 节省一次 5~20ms 的往返与反序列化。若存储敏感，可通过配置改为回表。

### 3.3 索引

```python
# 向量索引：HNSW + COSINE（5 万级数据下召回与延迟最优）
index_params = {
    "index_type": "HNSW",
    "metric_type": "COSINE",
    "params": {"M": 16, "efConstruction": 200},
}
# 检索参数
search_params = {"metric_type": "COSINE", "params": {"ef": 64}}

# 标量索引：加速 kb_id / source_type 过滤
client.create_index("finrag_embedding", "kb_id",       {"index_type": "INVERTED"})
client.create_index("finrag_embedding", "source_type", {"index_type": "INVERTED"})
client.create_index("finrag_embedding", "category",    {"index_type": "INVERTED"})
```

**规模扩容预案**：单集合超过 100 万条时，把 `kb_id` 设为 `partition_key`（分区键），
或将 IVF_FLAT(nlist=4096) 替换 HNSW；接口与代码不变。

### 3.4 写入与删除约定

| 操作 | 表达式 |
| --- | --- |
| 新增/更新切片 | `upsert(pk=f"chunk_{chunk.id}", ...)`，天然幂等 |
| 删除某文档全部切片 | `delete(expr=f'document_id == {document_id}')` |
| 删除某知识点 | `delete(expr=f'pk == "kp_{kp_id}"')` |
| 重建某知识库 | `delete(expr=f'kb_id == {kb_id}')` 后重新回填 |

**重要**：`document_chunk.id` 是 INSERT 后生成的自增主键，因此入库流程必须是
**先写 MySQL 拿到 id → 再写 Milvus**。这一顺序保障了「Milvus 失败可重放」。

### 3.5 零停机重建索引（reindex）

```
1. 创建 finrag_embedding_v2（同 schema）
2. 从 MySQL 分页读取，批量编码写入 v2
3. 校验 v2 数量 == MySQL 数量
4. alter_alias("finrag_embedding", "finrag_embedding_v2")  # 原子切换
5. 观察 24h 后 drop_collection("finrag_embedding_v1")
```

### 4.3 知识点编写规范（直接决定 85% 准确率）

1. **一题一知识点**：一条只表达一个可判定的结论，不合并多个要求。
2. **标题用问句或结论句**：便于与用户提问在同一语义空间（例：「商业银行流动性覆盖率的最低监管要求是多少」）。
3. **正文自包含**：不依赖上下文即可读懂，明确主体、条件、数值、时限。
4. **必须可溯源**：`primary_chunk_id` 必填，且 `quote_text` 必须能在原文中逐字检索到。
5. **数量化优先**：涉及比例、金额、期限、频次的必须写明确数值。
6. **时效标注**：能确定生效/失效日期的必须填写，判定规则见 §4.4。
7. **关键词 5~10 个**：包含同义词、口语说法、英文缩写（如「LCR、流动性覆盖率、Liquidity Coverage Ratio」）。

### 4.4 时效状态判定规则

```
若 superseded_by 非空                                  → amended（已修订）
否则若 expiry_date 非空 且 expiry_date < 今天          → repealed（已废止）
否则若 effective_date 非空 且 effective_date <= 今天   → effective（现行有效）
否则若 timeliness 由人工显式指定                        → 以人工为准
否则                                                  → unknown（未知）
```

系统中 `timeliness` 为**显式存储字段**（不做实时计算），由入库时的表单、批量导入文件、
或离线任务 `scripts/refresh_timeliness.py` 更新。检索时按 `timeliness` 加权：
`effective` × 1.0、`amended` × 0.9、`unknown` × 0.8、`repealed` × 0.5（可配置），
并在答案中主动提示引用条文已废止（FR-36）。

## 5. 数据量估算与容量规划

| 对象 | 单条大小 | 数量 | 小计 |
| --- | --- | --- | --- |
| `document_chunk.content` | ~1.5 KB | 30,000 | ~45 MB |
| Milvus 向量 | 1024 × 4 B = 4 KB | 31,000 | ~124 MB |
| Milvus 标量+正文 | ~2 KB | 31,000 | ~62 MB |
| 原始文件 | 平均 2 MB | 200 | ~400 MB |
| 问答记录 | ~3 KB | 50,000 | ~150 MB |
| **合计** | | | **< 1 GB** |

结论：单机 8GB 内存 / 40GB 磁盘完全满足，且留有三倍以上余量。

## 6. 数据访问约定（Repository 层规则）

1. **禁止裸 SQL 拼接**：全部走 SQLAlchemy 2.0 表达式或 ORM，防止注入（NFR-07）。
2. **分页统一**：`page` 从 1 开始，`size` 默认 10、最大 100；响应返回 `total/page/size/pages`。
3. **软删除**：`user`、`knowledge_base` 用 `status` 软删除；
   `document`、`knowledge_point` 用 `status='archived'`；物理删除仅通过管理接口显式触发。
4. **删除级联**（由 Service 编排，不用数据库外键级联，便于埋点与异常处理）：
   - 删文档 → 删 `document_chunk` + Milvus(`document_id`) + `knowledge_point_source` 中相关关联
     + 把受影响知识点的 `primary_chunk_id` 置空并标记 `verify_status='doubted'`
   - 删知识点 → 删 `knowledge_point_source` + `knowledge_point_relation` + Milvus(`kp_{id}`)
5. **时间字段**：统一 `DATETIME`，应用层使用带时区的 `Asia/Shanghai`，存储 UTC+8 本地时间。
6. **大字段**：`qa_message.content`、`document_chunk.content` 不进列表查询的 `SELECT`，
   列表接口必须显式指定返回列。

## 7. 初始化数据

`deploy/mysql/init/01-schema.sql` 负责建库建表 + 写入三个知识库 + `system_config` 默认项。

管理员账号**不在 SQL 中硬编码密码哈希**，而是由后端启动钩子执行
`app/db/seed.py` 创建/校正，默认账号 `admin / Admin@123`（首次登录强制改密为 P2 项），
可通过 `.env` 的 `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` 覆盖。
避免在 SQL 中出现明文或固定哈希带来的安全隐患。
