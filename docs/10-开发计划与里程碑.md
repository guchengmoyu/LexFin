# 10 · 开发计划与里程碑

> 总周期 **9 周**。按「先打通链路，再堆数据，最后调优」的顺序推进，
> **每两周必须有一个可演示的版本**，避免最后一周才发现链路不通。

## 1. 开发原则

| 原则 | 说明 |
| --- | --- |
| **契约先行** | 第 1 周冻结 `docs/03`（数据模型）与 `docs/06`（接口），之后前后端并行 |
| **纵向切片** | 每个阶段都产出「能跑通的最小闭环」，不追求某一层做到完美 |
| **数据并行** | **知识点收集从第 1 周就启动**，不要等到第 7 周才凑 1000 条（这是最大的进度风险） |
| **先粗后细** | 一期不做重排、不做 Redis、不做 ES，把 2 秒与 85% 先达标 |
| **可演示优先** | 每周五产出一个可演示版本 + 一段 3 分钟录屏，防止"代码写了一堆但演示不了" |
| **文档同步** | 接口/表结构/Prompt 变更必须同步改 `docs/`，代码评审时检查 |

## 4. 人员分工建议（4 人团队）

| 角色 | 主要职责 | 关键交付 |
| --- | --- | --- |
| **A 后端/RAG 主力** | 解析、切分、检索、Prompt、问答链路 | `app/rag/**`、`QaService` |
| **B 后端/平台** | 数据模型、接口、鉴权、任务、部署 | `app/api/**`、`app/models/**`、Docker |
| **C 前端** | 全部页面与交互、SSE、权限 | `frontend/**` |
| **D 数据/测试** | 文档收集、知识点整理、评测集、pytest + Apifox、性能测试 | `data/eval/**`、`tests/**`、`apifox/**` |

**说明**：D 的角色最容易被低估。**1000 条知识点是很重的数据工作**，
建议全员分摊：A/B/C 每人每周贡献 40 条，D 负责汇总校验与质量把关。
若团队只有 3 人，则 C 兼 D 的接口测试部分，知识点由全员平摊。

**分工协作要点**

1. `docs/03` 与 `docs/06` 是**共同契约**，任何改动需在群里同步并更新文档；
2. 前端需要后端接口未就绪时，用 **Apifox Mock**（内置，见 `apifox/README.md` §7）
   或按 `docs/06` 的示例响应自建 mock；
3. 每人每周五提交一段 2 分钟录屏，演示本周产出。

## 5. 关键路径与并行策略

```
关键路径（任一延迟都会推迟交付）：
  数据模型冻结 → Chunker → 向量入库 → 检索融合 → Prompt/LLM → SSE 问答 → 前端联调 → 评测调优 → 部署

可并行支线（不阻塞关键路径，但影响指标）：
  ├── 知识点收集与整理    ← W1 就启动，贯穿全程（最大进度风险）
  ├── 评测集构建          ← W4 可启动（不依赖系统完成）
  ├── Apifox 集合导入与场景搭建 ← 接口冻结后即可做（文件已就绪，导入即用）
  ├── Dockerfile / 部署   ← W6 可启动
  └── 文档与 PPT          ← W7 可启动
```

**必答问题预演**

| 可能被问 | 回答要点 |
| --- | --- |
| 2 秒响应怎么算的？ | 明确口径：TTFT（首 token）P95 ≤ 2s；检索接口 P95 ≤ 500ms。完整答案受外部模型限制，已用流式保证体感 |
| 85% 准确率怎么得出的？ | 110 题（含 10 题拒答）× 双人独立标注 × Kappa=0.82 × 4 条判据，原始明细可查 |
| 怎么防止大模型胡说？ | 三层防护：Prompt 强约束 + 无角标即拒答 + 可信度评分；并实测 10 题知识库外问题全部正确拒答 |
| 为什么用 Milvus 而不是 FAISS/pgvector？ | 课题推荐；原生支持标量过滤（知识库/时效），支持别名切换实现零停机重建；单机 standalone 与分布式 API 一致，可平滑扩容 |
| 为什么一期不上重排？ | 优先保证 2 秒时延；接口已冻结，开启只需改配置；评测脚本会给出开/关的准确率-延迟对比 |
| 知识点和切片什么关系？ | 切片是机器产物（重解析会重建），知识点是人工校验过的业务资产（可脱离文档存在），两者独立建表、多对多关联，检索时都召回并去重 |
| 增量更新怎么做？ | 已预留：`document.version` / `superseded_by` / `is_latest` + 时效状态机；二期实现自动重建时间线（FR-43） |
| 项目的难点在哪？ | 三条：条文级切分与页码溯源、中文混合检索的融合、在 2 秒内完成"检索+生成"并同时保证 85% 准确率 |
