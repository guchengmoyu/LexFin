# 02 · 系统总体架构设计

## 1. 架构目标与原则

| 原则 | 具体落地 |
| --- | --- |
| **分层清晰** | 路由层只做参数校验与响应封装；业务编排在 Service；RAG 算法细节在 `app/rag/`；SQL 与向量操作在数据访问层。任何一层不得越级调用 |
| **能力可替换** | LLM、Embedding、Reranker、向量库、OCR 引擎均通过工厂函数按 `.env` 装配，切换实现不改业务代码 |
| **契约先行** | 接口（`docs/06`）、数据模型（`docs/03`）先冻结，前后端并行开发 |
| **可观测** | 每个请求有 `request_id`，问答链路分段计时（改写/检索/重排/生成），写入响应体和日志 |
| **简单优先** | 一期单机 Docker Compose，无 K8s、无 MQ、无 Redis、无 ES（见 `docs/00` ADR-04~06） |
| **可演进** | 增量更新、时效标注、可信度、重排等能力在数据模型与接口上预留，二期接入不破坏契约 |

## 3. 逻辑分层职责

| 层 | 允许做 | 禁止做 |
| --- | --- | --- |
| **接口层** `app/api/v1/` | 解析入参、鉴权依赖、调用 Service、包装统一响应、SSE 输出 | 写 SQL、写 Prompt、写业务分支 |
| **服务层** `app/services/` | 事务边界、状态机流转、编排多个 RAG 组件、权限业务校验 | 直接拼 SQL 字符串、直接调 `pymilvus` |
| **RAG 能力层** `app/rag/` | 纯算法：解析、切分、编码、检索、融合、Prompt、调用 LLM、打分 | 访问业务表、感知 HTTP |
| **数据访问层** `app/models/` + `app/db/` | ORM 定义、Session 管理、迁移 | 业务判断 |
| **公共层** `app/core/` `app/utils/` | 配置、安全、日志、异常、常量、通用工具 | 依赖上层模块（避免循环引用） |

## 6. 核心时序

### 6.1 自然语言问答（SSE 流式，主链路）

```
用户   前端(Vue)      QA接口     RetrievalService    Milvus   MySQL      LLM
 │       │              │              │              │        │          │
 │─输入─▶│              │              │              │        │          │
 │       │─POST /qa/ask/stream(JWT)───▶│              │        │          │
 │       │              │─鉴权/限流/建会话             │        │          │
 │       │              │─QueryRewriter（P1：多轮改写）│        │          │
 │       │              │─retrieve(mode=hybrid)──────▶│        │          │
 │       │              │              │─向量 top20──▶│        │          │
 │       │              │              │─关键词 top20─────────▶│          │
 │       │              │              │◀─两路候选集──┴────────┘          │
 │       │              │              │─RRF 融合 → Rerank → Top5          │
 │       │              │              │─按 chunk_id 加载元数据───────────▶│
 │       │◀─SSE: meta（引用列表）───────│              │        │          │
 │       │              │─PromptBuilder（编号上下文）──┼────────┼─────────▶│
 │       │◀─SSE: token  │◀──流式 token ────────────────┼────────┼──────────│
 │◀逐字─│              │              │              │        │          │
 │       │◀─SSE: cites │─CitationResolver + Scorer     │        │          │
 │       │◀─SSE: done  │─落库 qa_message/qa_citation───┼───────▶│          │
 │       │◀─SSE: [DONE]│              │              │        │          │
```

**关键点**：`meta` 事件在检索完成后**立即**下发引用列表，使前端在 LLM 生成前就能渲染
「正在参考以下条文」，用户主观等待时间大幅缩短（NFR-02 的实现基础）。

### 6.2 文档入库（异步后台）


### 6.3 关键词检索（无 LLM，纯检索，低时延）

`GET /api/v1/search?q=流动性覆盖率&kb_id=1` →
QueryAnalyzer（分词、抽取文号/条号）→ MySQL FULLTEXT(ngram) 检索 →
按相关度 + 时效加权排序 → 返回 `<em>` 高亮的片段。**不调用 LLM，目标 P95 ≤ 300ms。**

## 7. 横切关注点设计

### 7.1 配置管理

`app/core/config.py` 用 `pydantic-settings` 单例 `settings`，所有可变项来自 `.env`（见 `docs/08`）。
代码中禁止出现裸常量，如端口、维度、chunk 参数、模型名、Top-K。

### 7.2 统一响应与异常

- 成功：`{"code": 0, "message": "success", "data": {...}, "request_id": "..."}`
- 失败：`{"code": 40xxx, "message": "中文可读信息", "data": null, "request_id": "..."}`
- 业务异常统一抛 `BizError(code, message, http_status)`，由全局处理器渲染；
  未捕获异常统一 500 + `code=50000`，日志记录堆栈但**不返回给前端**。
- 错误码分段见 `docs/06` §3。

### 7.3 日志与链路追踪

- `request_id`：中间件生成或透传 `X-Request-ID`，存入 `ContextVar`，
  由 loguru `patch` 自动注入每条日志，并在响应头与响应体中原样返回。
- 日志分级：`INFO` 记录请求行与耗时；`DEBUG` 记录检索候选、Prompt 全文（仅开发环境）；
  `ERROR` 记录异常堆栈。生产环境不打印 Prompt（含制度原文，体积大且敏感）。
- 问答链路必须打印结构化耗时：`rewrite=..ms retrieve=..ms rerank=..ms llm_ttft=..ms total=..ms`。

### 7.4 鉴权与权限

- 依赖链：`get_current_user`（解析 JWT） → `require_role(*roles)`（角色校验）。
- 路由声明式挂载：`dependencies=[Depends(require_role(Role.editor))]`。
- 一期不做数据行级权限（所有登录用户共享同一批知识库）。

### 7.5 事务与一致性

- MySQL 侧：切片写入、任务状态更新在**同一事务**内提交；Milvus 写入在其后执行。
- **最终一致性策略**：以 MySQL 为准。若 Milvus 写入失败，任务标记 `failed`，
  `document.status=error`，重试时按 `document_id` 先删后建（幂等）。
- 提供一致性巡检脚本 `scripts/check_consistency.py`：比对 MySQL `chunk` 数量与
  Milvus 按 `document_id` 过滤的实体数量，输出差异清单并提供修复入口。

### 7.6 幂等与并发控制

- 入库任务：同一 `document_id` 同时只允许一个进行中的任务（查询 `ingest_task` 状态拦截）。
- 向量写入：`pk = chunk.id`，`upsert` 天然幂等；重新解析时先 `delete(expr=f"document_id=={id}")`。
- 问答：无状态，天然支持并发；限流中间件保护 LLM 配额。
